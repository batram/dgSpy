# An upstream use-after-free, not a dgSpy regression: this file and both its
# collaborators were byte-identical to dnSpyEx when the crash was diagnosed.
# DbgRawMetadataImpl.ForceDispose released the native metadata buffers without
# setting `disposed`, so every reader's guard kept passing while the addresses
# were gone, and the process died of an AccessViolationException with no managed
# exception to explain it. Reproduced at roughly 23% of live smoke runs.
# Carried here because it kills our own gate; offer it to dnSpyEx and drop this
# entry when they take it. Setting `disposed` was a mitigation, not a cure, and
# the crash recurred at roughly one run in 25 -- a host would vanish a minute or
# so after a detach with nothing in any log. Deferring the free until the last
# reference is released was tried next and MEASURED NOT TO WORK: the reference
# holders are destroyed by the same teardown that frees, and the racing reader
# holds no reference at all, so refcounting cannot close this window in any
# arrangement. The fix carried now quiesces instead: teardown only marks every
# raw metadata disposed, and the actual free is posted to the engine's
# DbgDotNetDispatcher -- the one thread all metadata readers run on -- so a free
# runs behind any in-flight Roslyn compilation and can never overlap a read.
# Finalization is suppressed first: if dispatcher shutdown drops the post, the
# allocation is deliberately left for process exit because finalizer-thread
# reclamation cannot prove the last engine read has quiesced. Release() on an
# already-disposed object stays a no-op
# (it used to throw and abort DbgManagerImpl's close batch). See
# docs/local/dnspy-raw-metadata-use-after-free.md.
Extensions/dnSpy.Debugger/dnSpy.Debugger.DotNet/Metadata/Internal/DbgRawMetadataImpl.cs        upstream use-after-free on runtime teardown, fix carried pending an upstream PR
Extensions/dnSpy.Debugger/dnSpy.Debugger.DotNet/Metadata/Internal/DbgRawMetadataServiceImpl.cs upstream use-after-free on runtime teardown, fix carried pending an upstream PR

# Project export truncated names to 60 characters silently, and separate runs
# sharing one output directory then merged. FilenameCreator capped a project or
# file name at 60 and a namespace directory part at 40, cutting with no hash, no
# suffix and no message. Its usedNames set does de-duplicate, but it is in-memory
# and never seeded from disk, and MSBuildProjectCreator builds a fresh one per
# run -- so the guard holds within one invocation and not across two.
#
# Measured, not inferred: two assemblies whose names share a 60-character prefix,
# decompiled in two dnSpy.Console runs into one -o directory, both exit 0 and
# both print nothing. The result is a single folder holding the union of the
# source files and exactly one .csproj -- the second run's -- whose Compile list
# names only its own files. The first assembly's project file and AssemblyInfo.cs
# are gone; its source sits there orphaned. That is silent partial data loss, and
# it read as "assembly absent from the tree" in an audit here.
#
# Two changes, both additive. The limits move to FilenameLimits so a caller can
# raise them or pass 0 for none, defaults unchanged at 60 and 40. And truncation
# now says so: IMSBuildProjectWriterLogger gains Warning, deliberately separate
# from Error because a truncated name must not fail the run or flip the console
# exit code -- long assembly names are ordinary, and every existing caller kept
# its behaviour. Offer both to dnSpyEx; nothing here is dgSpy-specific.
